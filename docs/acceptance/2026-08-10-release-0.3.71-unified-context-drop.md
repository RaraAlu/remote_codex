## 实现结论

- 拖动来源只用于恢复 Remote Explorer 的真实 `vscode-remote:` URI 和审计，不再决定
  Composer 表示。所有 Bridge 受管资源都经一次性标记进入同一个原生 `@` 插入路径。
- Remote SSH 中的远端资源绑定远端主根；本机文件授权其父目录，本机目录授权其自身。
  授权根保存到当前窗口会话配置，Shim 在 thread/turn 边界只热刷新根列表，其他会话
  身份发生变化时失败关闭。
- 本机资源不复制到远端，也不能因绝对路径相似而交给 `remote_exec`。模型通过明确的
  `workspace_* target="local" rootId=...` 访问已授权本地次级根。
- 普通未带 Bridge 标记的官方 `chatgpt.addFileToThread` 不受兼容补丁改写。

## 实机结果

- 用户在前序本地回归中确认，文件可以从窗口外直接进入 Codex 面板，不再要求先经过
  Workbench 的非 Webview 区域；短行程和正常拖动进入同一受管接收链路。
- 2026-08-10 用户确认本次统一行为实际验证通过：本地与 Remote SSH 使用路径中的文件、
  目录均以当前 Composer 光标处的原生 `@` 表示，不再因 VS Code Explorer 或系统文件
  管理器来源不同而显示为附件。
- Remote SSH 中本机资源的授权目录和远端工作区根保持不同目标；本轮没有报告本机路径
  被当作远端路径、资源被复制到远端或 Composer 重复生成引用。
- 本轮没有重新执行兼容层禁用后的逐字节恢复、官方扩展升级后的重打补丁、Windows x64
  原生构建与实机，因此这些项目继续保留为发布门禁。
