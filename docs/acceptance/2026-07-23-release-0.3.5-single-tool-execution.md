## 问题复现与修复边界

- `0.3.4` 的真实官方 app-server 会把同一 `item/tool/call` 服务端请求广播给官方 stdio
  与外部 CLI 两条上游连接。两个独立 `ShimProxy` 都执行了请求。
- 修复前连续 5 轮、每轮 5 种工具的 25 个逻辑请求产生 50 条 `started` 和 50 条
  `succeeded`；每个 `requestId` 分别落到两个 `connectionId`。只读探针没有破坏数据，
  但同样行为会让非幂等 `remote_exec` 重复执行。
- `0.3.5` 在每个 `SharedAppServer` 内共享 `RemoteToolCallCoordinator`，按
  `threadId + turnId + callId` 协调请求，并校验完整参数指纹。首个执行产生的 Promise
  被所有广播副本复用；身份相同但参数不同的请求失败关闭。
- 官方 stdio 连接具有首选优先级；外部连接短暂等待首选副本，外部单独使用时仍会正常
  执行。完成结果保留 1 秒供迟到的广播副本复用，随后自动清理。

## Linux x64 实机证据

- VS Code `1.130.0` 的活动窗口为 `[SSH: g1_1]`，工作区根为
  `/home/unitree/rl_sar`。用户手动重载后，Bridge 日志记录托管 Shim 迁移到
  `0.3.5-b9fe412f87d0ca31`，并在 4.225 秒内从 `connecting` 进入 `ready`。
- 实测组件为 `openai.chatgpt@26.721.30844`、内置 Codex
  `0.146.0-alpha.3`、Remote SSH `0.124.0`、Bridge `0.3.5` 和 Executor `0.2.8`。
- 用户从官方面板创建的新 thread 成功调用一次 `remote_exec pwd`，最终回复
  `/home/unitree/rl_sar`。Codex 日志记录该 thread 和完成 turn，Bridge 审计只有一组
  `started/succeeded`。
- 外部对话控制客户端接入同一 thread 后再次发起 `pwd`。官方 stdio 与外部上游同时
  存在，最终回复 `BRIDGE_035_DEDUP_OK`；审计仍只有一个 `connectionId` 和一组执行。
- 随后 5 轮固定探针共 25 次逻辑调用全部成功，每种工具恰好 5 次开始和 5 次成功，
  没有重复 `requestId`，所有工作目录均为远端根。未建立第二条 SSH 认证链路，远端
  没有 Codex/app-server 进程。

## 打包边界与遗留风险

- Linux 使用已校验 SHA-256 的官方 Node `24.18.0` Windows x64 归档生成 SEA Shim，
  再运行 `npm run package:all`。Windows 包只含 `.exe`，Linux 包只含 `.cjs`；这只
  证明跨平台构包与内容隔离，不证明 Windows 运行时。
- 当前 `0.3.4 external-mcp` 的父进程是本次仍在运行的系统 Codex CLI，不是 VS Code
  重载产生的孤儿进程；这符合“已经运行的旧 CLI 不热加载新 Shim”的既有边界。CLI
  退出后的子进程归零仍需在生命周期目标中单独采集。
- 设置恢复、窗口关闭、relay 断线关闭握手、官方 UI 发起取消和 Windows x64 实机仍
  待补测。
- 最终结论：`0.3.5` 的多上游远端工具单次执行目标在 Linux x64 真实 Remote SSH
  链路通过；完整发布支持仍受生命周期和 Windows 实机门禁限制。
