## 根因与实现

- 官方 Codex Webview 将大段粘贴文本交给 Extension Host，再通过 app-server
  `fs/readFile`、`fs/createDirectory`、`fs/writeFile` 和 `fs/remove` 管理本机
  `~/.codex/attachments`。Shim 原先阻断全部本地 `fs/*` 请求，导致 Webview 的创建
  请求没有成功完成，界面一直显示“正在添加粘贴的文本…”。
- 例外只适用于 `clientSource=vscode` 的 RPC 请求。允许范围限定为 Codex 自管附件根
  中的注册表、UUID v4 目录和固定 `pasted-text.txt`，并逐方法约束参数和 10 MiB
  内容上限。外部 MCP/CLI、根外路径、其他文件名、未知 `fs/*`、通知和异常参数仍走
  原有 `-32003` 失败关闭路径。
- 审计使用 `local_attachment_request.forwarded`，只记录 `method` 和受管路径类别，
  不记录绝对路径、粘贴正文或 Base64。

- 强制安装 `codex-remote-bridge-0.3.51-linux-x64.vsix` 后，用户重载活动 `g1_1`
  Remote SSH 窗口。审计确认实际启动
  `0.3.51-ca4ff38000720b35/codex-bridge-shim`，连接模式为 `vscode-remote`。
- Bridge 在 `2026-07-31T01:25:29.846Z` 进入 `connecting`，app-server initialize
  后于 `01:25:37.103Z` 进入 `ready`；连接记录为
  `shimStarted=true`、`appServerInitialized=true`，没有建立第二条 SSH 认证链路。
- Webview 启动时的附件注册表读取在 `01:25:36.874Z` 以 `registry/fs/readFile`
  受限转发，不再记录为 `local_core_request.blocked`。
- 用户粘贴大段文本后，`01:28:35.242Z` 至 `01:28:35.249Z` 依次记录 UUID 目录创建、
  `pasted-text.txt` 写入和注册表写入；界面在有限时间内完成附件添加。
- 用户将附件恢复到输入框并随消息提交。`01:28:36.998Z` 至 `01:28:37.003Z` 记录
  注册表更新、固定粘贴文本删除和再次更新注册表。用户确认恢复内容与消息提交成功。
- 本次附件链路没有新的 `local_core_request.blocked`；审计条目不含附件路径、正文或
  Base64。官方日志中没有附件请求失败或 app-server 退出。
- 官方扩展仍记录本地 UI Extension Host 直接监视远端 POSIX 路径产生的既有
  `git-init-watcher ENOENT`，以及独立的设置服务 `403`。两者未阻断附件或任务提交，
  本修复也没有改写工作区 URI。
