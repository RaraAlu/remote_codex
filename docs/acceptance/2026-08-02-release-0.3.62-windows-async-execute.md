## 根因与实现

- 旧链路中，Controller 调用 `REMOTE_EXECUTOR_COMMAND` 后等待完整执行结果；Remote Executor
  仍在处理该跨主机命令时，同步调用 `REMOTE_OUTPUT_COMMAND` 把 stdout/stderr 反向发送给
  Controller。两个 Extension Host 因此互相等待，直到约 120 秒的上层超时解除阻塞。
- 新链路立即返回 `{accepted:true}`。Remote Executor 通过有界的延后事件队列，在当前命令
  返回后的下一事件循环按原顺序发送输出和 `executionComplete`；Controller 保持本地调用
  socket，流式投影输出并在终态到达后关闭。
- 新增 `controllerCommandAckMs`、`controllerFirstOutputMs`、`controllerCompletionMs`、
  `controllerOutputEvents` 与 `shimTransportTotalMs`，使确认、首段输出、终态和 Shim 端到端
  延迟可分开定位。
- 取消、幂等键、执行终态和 socket 意外断开语义保持不变；相关回归测试覆盖确认、输出顺序、
  完成、取消和关闭。

## 独立发现：外部 MCP 冷初始化身份兼容

- 标准外部 MCP 客户端使用 `clientInfo.name=codex_vscode_bridge_mcp` 时，两次独立冷连接均在
  约 `30.4 s` 超时；使用完全相同名称的原始 WebSocket 探针超过 40 秒仍未收到初始化响应。
- 同一网关和会话使用中性客户端名称 `bridge-raw-latency-probe` 时，初始化分别在 `6 ms` 和
  `5 ms` 完成。由此可将阻塞精确缩小到该客户端身份名称的兼容行为，而非一般网关或 Remote
  SSH transport 性能。
- 此项不属于本次前台命令重入修复，已作为 README 活动 TODO 保留；不得把后续暖连接结果
  写成冷连接为零。
