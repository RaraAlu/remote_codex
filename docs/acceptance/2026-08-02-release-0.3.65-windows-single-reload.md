## 问题与实现

- 旧实现把 `chatgpt.cliExecutable` 指向带版本和内容摘要的 Shim 路径。普通更新后，官方
  扩展会在新 Controller 更新设置前按旧路径启动；更新设置后还需要第二次重载才能运行
  新 Shim。
- `0.3.64` 候选曾把“仅 CLI 路径变化”改为不中途重载，但实机确认进程仍是旧
  `0.3.63` Shim，因此该候选未提交，也没有复用该版本发布最终行为。
- `0.3.65` 把官方设置固定为
  `%LOCALAPPDATA%/codex-remote-bridge/bin/official-launcher-v1/codex-bridge-launcher.exe`。
  Controller 仍安装内容寻址 Shim，但通过同目录 `current.json` 原子发布目标路径、完整
  SHA-256、当前 Extension Host PID 和更新时间。
- 稳定 launcher 等待与父 Extension Host PID 匹配的当前代际指针，验证目标位于托管
  `bin`、文件名正确且完整哈希一致，再用继承 stdio 启动目标。短时未发布新代际时保留
  有界旧指针降级，不建立第二条 SSH 或绕过能力检查。
- launcher 本体由 `launcher.json` 固定完整哈希，普通更新不替换；目标 Shim 通过受控
  环境字段获得原 Extension Host PID，并立即消费该字段，使运行状态、本地上下文和清理
  仍归属于实际 Extension Host，而不是中间 launcher。
- `remote.extensionKind` 发生变化时仍需要窗口重载；只有 CLI 路径修复且扩展宿主位置已经
  正确时继续当前激活。Remote Executor 首装或升级的独立自动重载语义未改变。

## Windows 实机证据

### 安装迁移与单次用户重载

- 安装 `0.3.65` 后，VS Code 扩展安装流程先刷新一次旧 Extension Host；官方扩展在
  Controller 迁移设置前仍抢先启动 `0.3.64` 内容路径。Controller 随后于
  `2026-08-01T22:01:08.971Z` 把设置迁移到稳定 launcher，并明确记录
  `continuing without another window reload`，没有调用 Bridge `reloadWindow`。
- 用户随后只手动重载一次。旧 Extension Host `272444` 于本地时间 `06:02:26.820` 正常
  退出；新 Bridge 于 `06:02:30.937` 激活。之后没有第二条 Extension Host 退出记录，也
  没有新的 `reloadWindow`、launcher 迁移或 Executor 安装日志。
- 新进程链为 Extension Host `295764` → 稳定 launcher `297172` → 当前 Shim `304528`；
  目标路径为 `0.3.65-d49076d74b129d40/codex-bridge-shim.exe`。三份相关二进制的完整
  SHA-256 与最终构建一致。
- `current.json` 的 `extensionHostPid=295764`，运行状态同样记录 `295764`，而
  `shimPid=304528`；证明中间 launcher 没有污染宿主身份。app-server 完成初始化且错误为
  `null`。
