## 问题与修复

精确 `0.3.34` 的独立失联探针在远端 `.codex-bridge-write.*` 出现后终止 Extension
Host。新 Extension Host 能自动启动，但旧写入把短 stdin 当作正常 EOF，以部分新内容
替换目标；调用方同时收到可重试 `REMOTE_TRANSPORT_DISCONNECTED`，存在错误重试风险。

修复分三层完成：

- 已发送副作用收到 `REMOTE_TRANSPORT_DISCONNECTED` 或 `SSH_DISCONNECTED` 响应时，
  Controller 提升为 `RESULT_UNKNOWN`，使用原幂等键查询结果，不自动重放；
- 远端原子写脚本接收声明字节数，只有临时文件大小精确匹配才允许替换目标；
- 写入在创建工作区临时文件前，先在 `/tmp` 创建包含规范工作区根和临时路径的受限
  登记。新 Executor 激活时只检查当前用户、死亡拥有 PID、当前打开工作区和严格匹配
  文件名的登记，清理对应临时文件后删除登记。

Executor 能力集合新增 `executeStdinExactLength` 和
`workspaceWriteOrphanCleanup`，诊断协议更新为 11。Controller 依据实际能力决定部署，
不使用 Executor 包版本或协议号作为运行时门禁。

## 结论

`0.3.37` 已在精确安装的 Linux x64 Controller、当前 Shim、自动升级的 Executor
`0.2.19` 和真实 `g1_1` VS Code Remote SSH transport 上关闭 Executor 独立失联写入
的数据完整性问题。调用方得到不可重试未知结果，原文件不被短流替换，死亡拥有者的
临时文件与登记由新 Executor 清理，原操作不重放。

该目标可以作为独立、已验证的 Linux 行为修复提交。它不是 `0.4.0` 发布通过声明；
README 中剩余官方 UI、审批/取消、视觉、权限撤销、最终窗口关闭和 Windows x64
范围继续保持 `待补测`。
