## 根因与修复

- Windows PATH 同时存在 npm 生成的无扩展 POSIX shim、`codex.cmd` 和 `codex.ps1`。
  旧解析顺序先选无扩展文件，产生 `ENOENT`；即使选中 `.cmd`，Node 直接 `spawn`
  也会返回 `EINVAL`。现在 Windows 按 `PATHEXT` 优先选择入口，并以安全的
  `ComSpec /d /s /c` 调用 `.cmd` / `.bat`；包含 cmd shell 元字符的入口失败关闭。
- 临时 VS Code thread 的 `thread/turns/list` 本身不受支持，不能证明 thread 可恢复。
  探测改为实际 `thread/resume(excludeTurns=true)`，明确 `no rollout found` 时启动新
  同步 thread。
- 窗口重载后，官方 UI 恢复历史任务的成功响应不一定返回完整 `result.thread`。共享
  网关现在跟踪 `thread/read`，并在成功的 read/resume/turn 请求中以请求内
  `threadId` 更新活动会话描述符。
- 显式 `--thread-id` 原先仍要求描述符活动 thread 相同，导致覆盖参数在探测前被拒绝。
  现在 PID/host/workspace 选择会话，显式 thread 只决定要探测或恢复的目标。
- 首次外部连接可能在官方 app-server 初始化缓存尚冷时等待。CLI 现在显示阶段进度；
  initialize 超时会主动关闭 WebSocket 并重试一次。只有实际 resume 成功才进入恢复，
  明确无 rollout 才新建，其他不确定错误直接上抛，不再伪装成可恢复。

## 遗留风险与结论

- Windows 不替换 npm 管理的 `codex` / `codex.cmd` / `codex.ps1` 文件；当前已验证入口是
  显式 `codex-vscode.exe`。普通无参数 `codex` 自动附着和无匹配会话透传仍是 POSIX
  托管 symlink 能力，Windows 如需同名入口必须另行设计可回滚且不破坏 npm 升级的方案。
- 官方扩展 `26.727.40816` 在 Windows UI Extension Host 中每 5 秒尝试监视
  `\\root\\work\\train\\MimicLite` 并记录 `git-init-watcher ENOENT`。Bridge 远端项目
  操作仍走活动 Remote SSH transport 且成功；按安全约束不能伪造工作区 URI。该官方
  前端兼容问题仍需单独处理或上游能力支持。
- Windows Node SEA 注入后仍提示原 Node 签名失效；当前以内容哈希、自动化和真实运行
  证明完整性，不声明 Authenticode 已签名。
- 最终结论：Windows x64 的 npm CLI 解析、显式外部 TUI、历史 thread 同步、无 rollout
  冷启动降级、外部 MCP 和退出清理在 `0.3.58` **限定范围通过**。完整 Windows 发布矩阵、
  普通 `codex` 同名自动入口、官方 git watcher 噪声与 Linux 当前候选仍保持活动 TODO。
