# Bridge `0.3.67` Windows Remote Extension Host 代理修复验收

日期：`2026-08-02`

执行人：用户手动重载 + Codex 只读诊断与可逆环境修复

## 范围

- 仅处理 Windows VS Code `1.131.0` 连接 Linux Remote SSH 时的 Extension Host 慢加载。
- 不修改 Bridge、Shim 或 Remote Executor 实现和协议；Controller 保持 `0.3.67`，Executor
  保持 `0.2.21`。
- 用户继续手动完成 SSH 密码输入和窗口重载；诊断与修复复用活动 VS Code transport，未
  发起第二条 SSH 认证链路。

## 修复前时间线

| 项目 | 第一次异常重载 | 第二次异常重载 |
| --- | ---: | ---: |
| `resolveAuthority(ssh-remote)` | `15,917 ms` | `4,139 ms` |

首次 SSH 解析的主要耗时是等待用户输入密码，不属于 Remote Extension Host 执行耗时；但
两轮连接后均真实出现 Remote Extension Host 无响应和 Executor 探测超时门槛告警。

远端 `remoteexthost.log` 显示，第二轮 Extension Host 于 `07:21:33.648` 启动，内置
`GitHub.copilot-chat` 于 `07:21:34.001` 激活，而 Executor 的 ping 激活直到
`07:21:42.903` 才开始。其间 Copilot 反复报告代理 socket 建立失败和
`ECONNREFUSED 127.0.0.1:32081`；本地 Renderer 同期在 `07:21:37.926` 至
`07:21:42.898` 将 Remote Extension Host 标记为无响应。

## 环境修复

- 远端 `32081` 端口没有监听进程。
- 失效的大小写两组 HTTP/HTTPS/ALL proxy 同时来自 `/etc/environment` 和
  `/etc/profile.d/bigbear-proxy.sh`。
- 显式清除代理变量后，远端访问 `https://api.github.com/` 返回 HTTP 200，证明当前环境
  不依赖该失效代理才能联网。
- 修改前完整备份为：
  - `/etc/environment.codex-remote-bridge-20260801T232821Z.bak`
  - `/etc/profile.d/bigbear-proxy.sh.codex-remote-bridge-20260801T232821Z.bak`
- `/etc/environment` 仅删除指向 `127.0.0.1:32081` 的六条代理项，保留 PATH 与
  NO_PROXY；`bigbear-proxy.sh` 原文件由上述备份保留并停止加载。修复后两个配置范围内的
  活动 `32081` 来源计数为 0。

## 结论与剩余门禁

失效远端代理是本轮 Remote Extension Host 无响应和 Executor 激活排队的直接环境原因；
修复后首轮实测已回到 2 秒门槛内。当前计为修复后连续稳定重载 1/3，仍需再完成两次普通
窗口重载，确认均无语言包重复更新、Remote Extension Host 无响应、额外自动重载，且
Executor 能力探测持续低于 2 秒，才能关闭 README 中的 Windows 更新环境 TODO。

本地 Extension Host 仍记录 Remote SSH `0.124.0` 的 `PendingMigrationError: navigator is
now a global in nodejs` 兼容告警；本轮未造成解析失败或修复后无响应，但后续两次门禁需继续
观察其是否引发 Extension Host 退出。
