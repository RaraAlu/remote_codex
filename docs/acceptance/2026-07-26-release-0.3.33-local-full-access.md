## 问题与修复

`0.3.32` 的外部 MCP 在用户选择 `full-access` 时发送：

```json
{"approvalPolicy":"never","permissions":"full-access"}
```

当前协议把 `permissions` 定义为命名权限档案 ID。普通本地共享网关保持官方请求语义，
因此 app-server 在 `thread/start` 具体失败为：

```text
default_permissions requires a [permissions] table
```

修复后的请求为：

```json
{"approvalPolicy":"never","sandbox":"danger-full-access"}
```

该字段形状已经由当前 app-server 的真实 `thread/start` 和项目操作证明可用，不依赖
任何组件版本值。普通本地网关原样传递 sandbox；Remote SSH 网关删除本地 sandbox，
映射到 Bridge 的命名本地拒绝档案，并继续把远端项目能力放在动态工具和既有审批边界
中。因而本地获得真实完全访问，Remote SSH 仍不能回退到本地项目执行。

## 普通本地实机

用户重载普通本地窗口后，活动进程为当前
`0.3.33-975ae2fee49d09fa/codex-bridge-shim.cjs`，会话描述符为 PID `1336490`、
`host=local`、`workspaceRoot=/home/zkbot`。

外部入口以 `full-access` 新建 thread
`019fa2a9-d790-7c31-8628-1ac43a27936d`，turn
`019fa2a9-d7d1-71b0-8447-56621428f439` 在 12,696 ms 内完成。Codex Core 真实执行一次
本地命令，读取候选 `package.json` 并运行 Git 根查询，结果为：

```text
codex-vscode-remote-bridge
0.3.33
/home/zkbot/work/remote
```

最终回复为 `LOCAL_FULL_ACCESS_0333_OK`。rollout 的 turn context 明确记录：

- `approval_policy=never`
- `sandbox_policy.type=danger-full-access`
- `permission_profile.type=disabled`
- `cwd=/home/zkbot`
- `workspace_roots=["/home/zkbot"]`

这证明普通本地窗口没有继承 Remote SSH 的本地拒绝档案，也没有因无效命名档案在
`thread/start` 失败。

用户重载 `g1_1` 后，Remote SSH Shim 同样来自当前 `0.3.33` 安装目录。`configuring`

  `rootRole=primary`、`remoteCwd=/home/unitree/mimiclite-sim2real`；

- 自动 IDE 选区只记录 URI、范围、大小和 SHA-256，正文不进入审计。

此前 thread `019fa2aa-ab13-7bc1-9c58-3ec1063b53fd` 已成功远端执行 `pwd` 和

Remote SSH rollout 仍显示本地控制进程使用只读 sandbox 和 Bridge 托管本地拒绝档案；

`019fa2b4-5226-7fc0-8a1e-a7b2b8549eaf` 在 37,480 ms 内实际发起 5 次 Codex Core

- 读取控制目录同名诱饵；

文件均不存在。

`956958306d24231d9ac11dbeecbf661329e5c35948b2c1c2a0781fefa8c9acc9`；再用

候选的普通本地与 `g1_1` Remote SSH 两条真实链路闭环。该提交可以作为独立、已验证的
Linux 行为修复保留。它不是 `0.4.0` 发布通过声明；官方 UI、最低量化、故障矩阵、
最终清理和 Windows 仍按 README 代办继续。
