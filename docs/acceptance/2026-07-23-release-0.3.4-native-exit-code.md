## 问题复现与修复边界

- 在活动 `g1_1` Remote SSH thread 中通过外部介入连续执行两轮只读回归。
  `remote_exec(["git","status","--short"])` 的结构化结果为退出码 `128`，模型最终总结
  也报告 `128`，但同一 turn 的 VS Code `commandExecution` 项显示 `exitCode=0` 和
  `status=completed`。
- 根因是投影层只按动态工具 RPC 是否完成生成 `0/1`，没有读取
  `ToolResult.data.exitCode`。远端执行器、传输、模型输入和审计没有丢失该值。
- 修复后，`remote_exec` 和 `remote_git_status` 优先保留结构化结果或错误详情中的实际
  退出码；收到信号且退出码为 `null` 时保留 `null` 并标记失败。其他远程读、列目录和
  搜索工具继续按工具调用成功状态投影。
- 命令非零退出仍属于一次成功完成的 Bridge RPC，不改写为传输错误；仅原生命令项准确
  显示失败状态、退出码和 stdout/stderr。

## Linux x64 实机证据

- 本地 VS Code `1.130.0` 的活动窗口为 `[SSH: g1_1]`，规范远端根为
  `/home/unitree/rl_sar`；复用现有 VS Code Remote SSH transport，没有启动第二条 SSH
  认证链路，也没有修改远端项目文件。
- 实测组件为 `openai.chatgpt@26.721.30844`、其内置 Codex
  `0.146.0-alpha.3`、Bridge `0.3.4`；系统 Codex `0.145.0` 只作为外部客户端。
- 外部客户端恢复已有 thread 后执行两轮只读 `remote_exec`。第二轮同时接入只读
  WebSocket 观察器，捕获的 `item/completed` 为 `type=commandExecution`、
  `status=failed`、`exitCode=37`，并保留 stdout/stderr 和远端工作目录。
- Bridge 审计记录两轮审批为自动全访问、操作均为远端 `remote_exec`，工作目录均为
  `/home/unitree/rl_sar`；远端进程检查没有 Codex/app-server。
- 外部客户端和观察器均已正常退出。该结果证明本目标的 Linux 外部 CLI 投影，不替代
  官方面板按钮发起、全套固定探针和三类生命周期关闭验收。

## 打包边界

- Linux 首次运行 `npm run package:all` 因没有 Windows SEA Shim 失败。随后使用与本机
  Node `24.18.0` 同版本的官方 Windows x64 归档，校验官方 SHA-256 后在 Linux 生成并
  注入通用 SEA blob；第二次 `npm run package:all` 成功。
- Windows VSIX 只含 `.exe` Shim，Linux VSIX 只含 `.cjs` Shim；该交叉构包只证明
  Windows 产物构造和内容隔离，不证明 Windows Extension Host、Shim 或 Remote SSH
  运行时。

## 遗留风险与结论

- 待补测：官方面板按钮发起、完整固定探针、设置恢复以及窗口关闭后的 relay/MCP
  遗留进程指标。
- 待补测：Windows x64 本机构建、Shim 冒烟和真实 Remote SSH 运行。
- 已知生命周期现象：切换 Remote SSH 窗口时，旧 UI 拥有的 gateway 会终止外部客户端，
  已观察到一次“未完成关闭握手即重置”的 WebSocket 错误；本目标没有修改该行为。
- 最终结论：`0.3.4` 的退出码投影目标在 Linux x64 真实 Remote SSH 外部 CLI 链路通过。
- 支持声明：只声明 Linux x64 的本目标实机和双平台包内容已验证；完整发布与 Windows
  运行支持仍受上述 `待补测` 门禁限制。
