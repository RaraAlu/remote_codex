| 变更摘要 | 外部 CLI/MCP 客户端断开时，按客户端取出仍活动的 turn，向共享 app-server 请求中断并等待确认，避免留下永久 `inProgress` turn |
| 命中的升级触发项 | Controller/Shim、官方 app-server、外部 CLI、VS Code Remote SSH、断线与生命周期 |
| 声明范围 | Linux x64 自动化、原生构包及 `g1_1` 真实 Remote SSH 外部 CLI 中途断连；Windows 暂停推进 |

- turn 所属客户端由既有 thread/turn 跟踪器记录；断连只取走该客户端拥有的活动 turn，
  不影响官方 UI 或其他外部客户端的 turn。
- 每个中断请求使用独立 RPC ID，最多等待 2 秒；审计分别记录请求数、确认数和未确认数。
- 只有全部中断得到无错误响应时，`external_cli.disconnect` 才记为 `succeeded`；
  上游关闭、错误响应或超时均记为 `unknown`，不把未知状态伪装成成功。
- Shared app-server 退出前等待已触发的断连清理任务，避免关闭阶段丢失中断和审计。

## `0.3.29` 缺陷复现

目标为 Remote SSH 主机 `g1_1`，规范工作区为
`/home/unitree/mimiclite-sim2real`。全程复用活动 VS Code Remote transport，没有启动
第二条 SSH 连接，也没有密码提示。

- 外部 CLI 创建 thread `019fa20e-d579-71e3-9797-7db85add3f0b` 和 turn
  `019fa20e-d5b5-7271-bfb0-365912b3a432`，在命令工具进入执行阶段时断开。
- 断开后远端标记进程为 0，也没有形成 `remote_exec started` 审计，但 turn 长时间保持
  `inProgress`；外部客户端已不存在，无法自行完成该 turn。
- 为清理失败样本，随后才通过 Bridge MCP 显式执行一次 `turn/interrupt`。该人工清理
  不计入 `0.3.29` 产品成功结果。

根因是外部 socket 关闭路径只关闭该客户端的上游和 Executor 会话，没有中断已由该
客户端启动、仍由共享 app-server 持有的 turn。

## `0.3.30` 实机复测

### 重载与身份

- 用户安装候选并重载后，当前 Extension Host PID 为 `1233709`，共享 app-server/Shim
  PID 为 `1233961`；旧 Extension Host 已退出且旧会话文件不存在。
- 当前 Controller 为 `0.3.30`，Shim 路径包含
  `0.3.30-8aedab7317ae1dac`，官方扩展仍为 `26.721.41059`。
- Bridge 审计从 `configuring`、`connecting` 到 `ready`，远端主机和工作区根分别为
  `g1_1` 和 `/home/unitree/mimiclite-sim2real`。

### 断连样本一

- 外部 CLI 创建 thread `019fa216-1d5a-7940-b701-f8fe39bffe38` 和 turn
  `019fa216-1d94-7950-9133-4548f25cad5c`，以 `full-access` 自动审批启动一次
  `remote_exec`。
- 审计确认 `remote_exec started` 后立即断开客户端；`external_cli.disconnect`
  在 8 ms 内记录 `requested=1`、`confirmed=1`、`unconfirmed=0`。
- 未调用人工中断。3 秒后通过独立 Bridge MCP 重读，turn 已为 `interrupted`，持续
  6,539 ms。

### 断连样本二与进程清理

- 为排除短命令自然退出的假阳性，另建 thread
  `019fa218-6d68-71e1-b17f-740054a25c7f` 和 turn
  `019fa218-6da1-7361-ab28-4225cfa0daeb`，启动带唯一进程名的 120 秒远端命令。
- 只有审计确认 `remote_exec started` 后才强制断开 WebSocket；断连清理耗时 7 ms，
  中断汇总仍为 `requested=1`、`confirmed=1`、`unconfirmed=0`。
- 断连审计落盘后立即通过当前 VS Code transport 扫描远端 `/proc`，唯一标记进程数为
  0，证明不是等待 120 秒自然结束。
- 约 5 秒后重读，turn 为 `interrupted`，持续 5,718 ms；没有调用人工中断，也没有
  重放原命令。

### 已知表现

- 官方 app-server 返回的 interrupted turn 中，内部 `commandExecution` item 快照仍可
  显示 `inProgress`；turn 本身已具备 `completedAt` 和 `interrupted` 终态，远端进程
  已归零。后续官方协议若提供 item 级取消终态，再单独收敛展示一致性。
- 客户端断开同时会关闭其 Executor transport。已失去响应通道的工具调用审计可在恢复
  超时后落为 `RESULT_UNKNOWN`；这不改变本次已单独确认的 turn 中断和远端进程清理
  结果，也不把工具副作用记成成功。
