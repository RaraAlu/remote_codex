## 问题复现

官方 `openai.chatgpt@26.721.41059` 的编辑器“加入对话”和文件加入处理只接受
`file:` URI，而 Remote SSH 编辑器使用 `vscode-remote:` URI。`0.3.31` 官方线程
`019fa26b-b210-7400-977d-ec26a7a8321b` 的当前选区样本在 7,963 ms 后完成，但
rollout 的 `text_elements` 为空，回复没有看到预置标记；普通远端文件也无法从官方
附件入口加入。这是官方 UI 对远端 URI 的实际能力缺口，不是用户选择了错误文件。

最初实现的一轮显式 Bridge 附件已在真实窗口证明可传递远端 URI 和选区，但用户要求
接近原生 Codex 的 IDE 背景体验，不接受每轮手工加入。最终候选因此改为逐轮自动采集，
显式命令只保留为可选覆盖。

## 实现与安全边界

- Shim 在每个 Remote SSH `turn/start` 上通过当前 Controller VS Code transport 请求
  `resolveEditorContext`，不启动 OpenSSH 或第二条认证链路。
- Controller 每轮读取 `activeTextEditor`。非空选区只注入选区；空选区注入完整活动
  文件。快照来自 VS Code 文档内存，因此包含当前未保存编辑内容。
- URI 必须与当前 Remote SSH 工作区的 scheme、authority 和规范 POSIX 主根一致。
  上下文保留 `vscode-remote` 工作区 URI、相对路径、稳定资源 URI、语言、范围、大小
  和 SHA-256，不改写或镜像成假的本地项目 URI。
- 显式文件或选区命令产生 `origin=explicit` 的一次覆盖；没有覆盖时每轮生成新的
  `origin=automatic` 快照和 context ID。
- 没有活动编辑器、活动项不属于远端主根、二进制或超过 128 KiB 时不附加可选背景，
  不阻断普通任务。Controller transport、配置身份、消息结构、大小或哈希完整性异常
  仍失败关闭。
- 审计只记录来源、哈希、范围、URI 和大小；不记录编辑器正文。

## 真实 Remote SSH 结果

### 最终候选重载

用户重载最终加固 Linux VSIX 后，Extension Host 使用新会话，Shim 路径切换到
`0.3.32-db73bb4957f24dd7`。Bridge 从 `configuring` 到 `ready` 为
`07:51:41.039Z -> 07:51:44.270Z`，耗时 3,231 ms。当前 session 配置同时保留规范
远端主根与已授权本地次级根，旧 Shim 内容没有继续接管新任务。

### 自动选区

注入准备线程 `019fa286-df4e-7771-83c4-1d8a6c59d649` 只调用一次
`workspace_open_file`，将远端 `current-editor.txt` 第 2 行选中。随后新线程
`019fa287-1be1-7c93-801c-344eaa181c21` 不调用工具，在 6,462 ms 后准确返回：

- 远端相对路径和 `vscode-remote://ssh-remote%2Bg1_1/...` URI；
- `origin=automatic` / `kind=selection`；
- 30 字节预置选区正文。

rollout 明确包含自动采集提示、真实 URI 和选区正文。审计只包含对应 SHA-256、范围、
大小和 URI，不含正文。

### 自动完整文件

准备线程 `019fa287-7090-7a33-ad3a-c20dc01d4bfd` 将
`ordinary-attachment.txt` 打开为空选区。样本线程
`019fa287-bf47-7e92-bdb0-4e6e3e55284b` 不调用工具，在 6,607 ms 后准确返回远端

`kind=file`、`selection=null`，正文仍未进入审计。

### 本地次级根隔离

准备线程 `019fa288-2168-7550-89cf-f6be184ae774` 在同一远端窗口打开授权本地次级根
的同名虚拟资源。下一线程 `019fa288-51be-7d12-b94d-e87383301a9a` 在 5,870 ms 后
完成，rollout 中不存在 Bridge 编辑器上下文键、本地或远端同名诱饵正文；审计也没有
为该轮写入 `editor_context.inject`。因此 `codex-bridge:` 本地资源没有被误判为远端
IDE 背景。

### 官方面板直接任务

Codex 先用 `workspace_open_file` 恢复远端第 2 行选区，用户随后从官方面板直接新建
线程 `019fa28a-ba59-7330-b68c-ff9478ffebe4`，没有点击附件或 Bridge 上下文命令。
官方日志在 `22:47:08.573` 创建 conversation，`22:47:08.605` 解析 turn-start，
32 ms 内进入请求；没有 `Unknown local project`。turn 在 9,020 ms 后完成并准确返回
远端相对路径、真实 URI、自动选区来源和完整预置正文。

官方 Webview 与其 fetch handler 都请求了该轮背景，二者得到相同正文哈希但不同的
新 context ID；实际 conversation 只有一个 completed turn。rollout 只有本轮自动
背景，未使用官方 `text_elements` 附件。该 UI 样本来自最终失败关闭加固前的同版本
功能候选 `0.3.32-4171e9b4061a7bbb`；加固只收紧上下文大小、形状、身份失败和显式
覆盖销毁，不改变成功路径。

### 普通本地窗口诊断

对已有普通本地会话 PID `1285882` 使用 `on-request` 外部入口，新线程
`019fa293-4bdc-7d53-b962-d954e107e390` 在 6,148 ms 后完成并返回
`LOCAL_WINDOW_SEMANTICS_0332_OK`。这只证明本地共享 app-server 的默认权限路径可以
创建和完成 turn；该样本没有调用项目工具，而且会话仍运行旧 `0.3.31` Shim，不能作为
当前候选的本地项目语义验收。

同一会话选择 `full-access` 时，官方 app-server 在 `thread/start` 以
`default_permissions requires a [permissions] table` 失败。当前外部入口发送
`permissions="full-access"`，但普通本地共享网关不会像 Remote SSH 会话那样把它映射
为 Bridge 权限档案。这是独立实现缺口，后续必须按实际能力和消息形状修复并升级根包，
不能用本次 `on-request` 成功掩盖。
